1. 项目概览

CH 是一个面向中文内容场的自动化生产 + 分发流水线。原始素材（RSS、HTML、Reddit、Bluesky、X 等）经过 8 个职责单一的 agent 串联，最终落地为站内文章并向社媒分发。

核心特征

  • Agent 解耦：每个 agent 一个 BullMQ 队列，前一步把下一步的任务直接 enqueue，失败可独立重试。
  • 状态机驱动：items.status 是单一事实源，下游 agent 用状态守门，避免重复消费。
  • 可降级：每个 LLM agent 都有 *_SKIP_LLM=1 规则版兜底，可在没有 LLM 配额时跑通流水线。
  • 人工闸口：publishing 和 distribution 是硬人工卡点，auto-pipeline 不会自动触发。
  • 可观测：每个 agent 调用都写 agent_runs（耗时、token、成本、错误）。

2. 系统架构

流水线全景

source-scoring → ingestion → classify-title → cover → compliance → publishing* → distribution* → analytics
* 标记的 agent 是人工闸口，auto-pipeline 不会自动触发

状态机

INGESTED → CLASSIFIED → TITLED → COVERED → COMPLIANCE_PASS | COMPLIANCE_REVIEW | COMPLIANCE_FAIL → PUBLISHED → DISTRIBUTED

每个 agent 都做 WHERE status IN (...) 守门，串错状态会自动跳过（{skipped: true}），不会污染 agent_runs。

3. 8 个 Agent 详解

每个 agent 都住在 apps/api/src/workers/<name>/，导出一个 start*Worker()（被 workers/index.ts 注册），以及一个直接调用的 *One()（admin/测试用）。所有调用都包在 withRun() 里，自动写 agent_runs。

[1]

source-scoring

为信源打分（0-100），决定其在 ingestion 灰度池里的权重，给低质源降级或拉黑。
核心函数
scoreAllSources() · workers/source-scoring/scorer.ts
实现方式
纯 SQL 聚合，不调 LLM。融合发布数、合规失败率、最近 7 天活跃度、PV、收入。
触发
auto-pipeline 周期性 enqueue，或 admin 手动调 /admin/day5/score-now。
副作用
更新 sources 的 score / risk_level / stability / status。
下一步：无（独立任务，结果被 ingestion 灰度阶段读取）
[2]

ingestion

从激活信源拉取最新内容，去重 + 清洗后落库。
核心函数
ingestSource(sourceId) · workers/ingestion/index.ts
子模块
adapters/（rss / html / reddit / bluesky / x / knit / json-2ksg / sitemap-images）
clean.ts（Mozilla Readability）· dedupe.ts（dedupe_key + content_hash）· simhash.ts（语义近邻，阈值 3/63）· persist.ts（写库）
三层去重
① URL 级 dedupe_key　② 源内 content_hash　③ 源内 simhash 模糊匹配
灰度
sources.grayscale_pct 控制本轮被采概率（默认 100）。
失败
认证失败抛 AdapterAuthError，工作台高亮。其他错误进 stats.errors。
下一步 → enqueue classify-title，jobId = classify-title__<itemId>（去重）
[3]

classify-title

合并的 分类 + 标题 agent。两步连跑省一次队列跳。
核心函数
classifyTitleOne(itemId) · workers/classify-title/index.ts
步骤
① 分类（taxonomy 映射，输出 category + tags + keywords）
② 标题（生成 N 个候选 + 选最优 + 摘要 + 唯一 slug）
降级
CLASSIFICATION_SKIP_LLM=1 · TITLE_SKIP_LLM=1，走关键词分类 + 原标题保留。
幂等
状态守门：仅处理 INGESTED / CLASSIFIED / TITLED，重跑只升 title_version。
下一步 → enqueue cover，jobId = cover__<itemId>
[4]

cover

从 raw_items.media_urls 里挑最优封面（按分辨率 + 长宽比打分），多尺寸压制后传 S3，再生成封面文案。
核心函数
coverOne(itemId) · workers/cover/index.ts
子模块
select.ts（多源反盗链下载 + sharp 元数据）· resize.ts（多尺寸输出）· storage.ts（S3/MinIO 上传）· caption.ts（封面文案）
反盗链
对 2ksg/knit/x 等带 Referer/Cookie 头部下载。
HTML 源加挂图集
platform=html 时取 Top-6 作为 gallery，存入 cover_sizes.gallery。
降级
COVER_SKIP_LLM=1 时 cover_copy = 文章标题。
下一步 → enqueue compliance
[5]

compliance

两层风险审核：L1 正则黑名单（cheap）+ L2 LLM 6 维度打分。
核心函数
complianceOne(itemId) · workers/compliance/index.ts
L1 黑名单
政治 / 色情 / 版权水印 三类正则，命中即 FAIL（blacklist.ts）。
L2 LLM 评分
6 个维度 0-3 分（政治 / 色情 / 暴力 / 版权 / 医疗夸大 / 金融诱导）。最大值 ≥3 → FAIL；≥2 → REVIEW；其余 → PASS。
决策
decide() 单元函数，黑名单永远优先。LLM 失败默认进 REVIEW（保守）。
降级
COMPLIANCE_SKIP_LLM=1：黑名单干净就合成全 0 分，自动 PASS。
PASS 才 → enqueue publishing。FAIL/REVIEW 留在状态等人工。
[6]

publishing

人工闸口
把 COMPLIANCE_PASS 的文章正式上线，写 published_url，触发 ISR 刷新。
核心函数
publishOne(itemId) · workers/publishing/index.ts
动作
① 补/重用 slug　② 写 published_url + published_at　③ POST /api/revalidate 刷四个路径（首页、文章、分类、sitemap）
strict 模式
PUBLISH_STRICT=1：仅 COMPLIANCE_PASS 可发布。默认宽松（兼容历史数据）。
失败容忍
revalidate 失败不阻塞发布（fire-and-forget）。
手动触发：admin UI 的 publish queue / POST /admin/pipeline/approve-publish
[7]

distribution

人工闸口
为已发布文章生成社媒推文，写入 distribution_tasks 等待执行。当前默认 channel=twitter。
核心函数
distributeOne(itemId, channel) · workers/distribution/index.ts
改写
rewrite.ts::rewriteForTwitter：Sonnet 模型，280 字符预算（含 t.co 占位 23 字符），结尾 2-3 个 hashtag。
降级
DISTRIBUTION_SKIP_LLM=1：标题截断 + 标签拼接 + 链接，纯规则。
幂等
同 item + 同 channel 已存在记录就跳过。
实际投递
当前只入库，由人工或外部 worker 消费 distribution_tasks WHERE status='pending' 实际推送。
手动触发：POST /admin/day6/distribute/:id · /admin/day6/distribute-all
[8]

analytics

数据回流（GA4 拉昨日 PV/UV）+ 每周生成 markdown 报表。
核心函数
pullAnalyticsYesterday() · ga4.ts
generateWeeklyReport() · report.ts
GA4 拉取
需 GA4_PROPERTY_ID + GOOGLE_APPLICATION_CREDENTIALS，按 /a/<slug> 维度抓 PV/UV/平均时长。无凭证时优雅降级返回 {upserted:0, skipped:0}。
周报
近 7 天总 PV/UV/收入 + 每日趋势 + Top 10 文章 markdown 表格。
调度
cron ANALYTICS_CRON（默认 0 2 * * *，每天 2 点拉）。
无下游（终点）。结果反哺 source-scoring 的 PV/收入加分项。

4. 数据模型

schema 在 packages/db/migrations/，0001_init.sql 是核心。

表作用关键字段
sources 上游账号 / 信源 platform, external_id, score, risk_level, status, config, grayscale_pct
raw_items 采集到的原始数据 source_id, url, dedupe_key (UNIQUE), content_hash, simhash, media_urls
items 处理中的文章（流水线主表） status, category, tags, title, slug (UNIQUE), cover_url, cover_sizes, compliance_*, published_url
distribution_tasks 多渠道分发任务 item_id, channel, copy, status, scheduled_at, executed_at
analytics_daily 日级流量 + 收入 PK = (item_id, date, channel) · pv, uv, avg_duration, revenue
agent_runs 每次 agent 调用的审计 agent, item_id, status (running/success/failed), model, tokens, cost_usd, latency_ms, error
状态守门约定：每个 agent 的 *One() 第一行就检查 items.status 是否在允许列表内，不在就 return {skipped: true}，不写 agent_runs 错误，不消耗重试预算。

5. 队列与运行时

BullMQ 队列

8 个队列与 8 个 agent 一一对应，名字在 packages/agents/src/queue.ts::QUEUE_NAMES：

source-scoring · ingestion · classify-title · cover ·
compliance · publishing · distribution · analytics

默认作业策略（queue.ts）：

  • 重试 3 次，指数退避（500ms 起）
  • 成功保留 7 天 / 5000 条；失败保留 30 天
  • jobId 模板：<agent>__<itemId>，天然去重，并发触发只跑一次

auto-pipeline

auto-pipeline.ts 每 AUTO_PIPELINE_INTERVAL_MS（默认 15s）扫一次：

  • 仅当 agent 在 autoState 开启 + 不在 pausedState + 没有 emergency stop
  • 队列 waiting+active < 10 才补单（避免堆积）
  • HARD_HUMAN_GATES = {publishing, distribution}，永远不会被 auto 触发

调度（scheduler.ts）

  • ingestion fanout cron：默认 0 * * * *（每小时整点），可改 INGESTION_CRON
  • analytics pull cron：默认 0 2 * * *（每天 2 点）
  • 关闭：设 DISABLE_SCHEDULER=1 或 DISABLE_AUTO_PIPELINE=1

告警

alerts.ts 周期检查队列堆积和 LLM 失败率，超阈值发告警（Sentry/Webhook）。阈值：ALERT_QUEUE_THRESHOLD、ALERT_LLM_FAIL_RATE。

6. 快速开始

前置条件

  • Node ≥ 20.10、pnpm 9
  • Docker + Docker Compose
  • （可选）Groq API key — 跑 LLM agent 时需要；不配也能用 SKIP 模式跑通

一键启动

# 1) 复制环境变量模板
cp .env.example .env
#    填 GROQ_API_KEY（或留空用 SKIP_LLM 模式）

# 2) 起基础设施（MySQL / Redis / MinIO）
pnpm infra:up

# 3) 安装依赖
pnpm install

# 4) 跑数据库迁移
pnpm migrate

# 5) （可选）灌种子数据 / 信源
pnpm seed

# 6) 起开发环境（API :4000 + Web :3000 并行）
pnpm dev

验证

curl http://localhost:4000/health
# → {"ok":true,"ts":...}

curl http://localhost:4000/agents
# → {"agents":["source-scoring","ingestion",...]}

open http://localhost:3000           # 站点首页
open http://localhost:3000/admin     # 控制台
open http://localhost:9003           # MinIO console (minioadmin/minioadmin)
注意：docker-compose 里 MySQL 映射到宿主 3306、Redis 到 6381、MinIO 到 9002/9003。.env 必须用这套端口。

12. 故障排查

常见问题

API 起不来 / DB 连不上

  • 检查 docker compose ps 是否 healthy
  • 确认 .env 用的是 docker-compose 实际映射的端口（5433/6381/9002）
  • 跑一遍 pnpm migrate 确保 schema 是最新

队列堆积、worker 不消费

  • GET /admin/day7/queues 看具体哪个 queue 堆
  • 看 agent 是不是被 paused：GET /admin/pipeline/state
  • 批量重试失败：scripts/retry-failed.ts
  • 清空 failed：scripts/clear-failed.ts

LLM 调用失败 / 没配额

  • 临时设全部 *_SKIP_LLM=1 跑通流水线
  • 看 agent_runs.error 字段定位错误码（429 / 5xx 由 callClaude 自动重试 3 次）

合规 REVIEW 队列堆积

  • 多半是 LLM 调用失败 → fallback 到保守 REVIEW
  • 人工放行：POST /admin/pipeline/approve-review/:itemId
  • 批量重检：POST /admin/day4/recheck/:id

封面下载 403 / 空 body

内容中台 · 使用说明（运维版）

假设你能用 curl、看 JSON、知道环境变量怎么配 — 但不需要改源码

所有日常操作都通过 Web 后台 UI 或 HTTP API 完成。这份文档以 API 为主线（写脚本和排查更直接），UI 会在每个场景里指出对应入口。

API 基础地址：http://<your-api-host>:4000 · Web 后台：http://<your-web-host>:3000/admin

1. 每天上班先做的 3 件事

看健康状态 
curl http://localhost:4000/health
# → {"ok":true,"ts":...}  正常
看队列堆积 
curl http://localhost:4000/admin/day7/queues
# 看每个队列的 waiting / active / failed
# 任何一个 failed 涨得快、或 waiting 突然破百，就要排查
看告警 
curl http://localhost:4000/admin/day7/alerts
# 看最近的告警记录（队列堆积、LLM 失败率超阈值等）

2. 信源管理

添加一个信源

curl -X POST http://localhost:4000/admin/sources \
  -H 'content-type: application/json' \
  -d '{
    "platform": "rss",
    "external_id": "techcrunch",
    "name": "TechCrunch",
    "url": "https://techcrunch.com/feed/",
    "config": {}
  }'
# 返回 {id: "..."}  信源默认 status=active, grayscale_pct=100

支持的 platform

rss标准 RSS / Atom feed
htmlHTML 列表页（Readability 解析）
redditReddit subreddit JSON
blueskyBluesky AT Protocol
xX / Twitter（需 cookie）
knit · 2ksg专项站（图集类）
sitemap-images站点地图图片源

带反盗链 / 鉴权 cookie 的源

curl -X POST http://localhost:4000/admin/sources \
  -H 'content-type: application/json' \
  -d '{
    "platform": "knit",
    "external_id": "knit-feed-1",
    "name": "Knit Feed 1",
    "url": "https://xx.knit.bid/...",
    "config": {
      "cookie": "cf_clearance=xxx; ...",
      "userAgent": "Mozilla/5.0 ..."
    }
  }'

修改 / 暂停 / 删除

# 改名字或 config
curl -X PATCH http://localhost:4000/admin/sources/<id> \
  -H 'content-type: application/json' \
  -d '{"name":"new name"}'

# 暂停（不再采集，但已有数据保留）
curl -X PATCH http://localhost:4000/admin/sources/<id> \
  -H 'content-type: application/json' \
  -d '{"status":"inactive"}'

# 删除（默认保留已采集 items；?cascade=1 级联删）
curl -X DELETE 'http://localhost:4000/admin/sources/<id>?cascade=1'

立即采集一次（不等 cron）

# 全部信源 fanout
curl -X POST http://localhost:4000/admin/ingest/fanout

# 单个信源（async=1 异步入队，否则同步等结果）
curl -X POST 'http://localhost:4000/admin/ingest/source/<id>?async=1'

调整灰度（控制采集频率）

# 把某源的灰度调到 30%（每轮有 30% 概率被采）
curl -X PATCH http://localhost:4000/admin/day7/sources/<id>/grayscale \
  -H 'content-type: application/json' \
  -d '{"pct":30}'

# 一键把所有源调到 50%
curl -X POST http://localhost:4000/admin/day7/grayscale-all \
  -H 'content-type: application/json' \
  -d '{"pct":50}'

看哪些源认证失败

curl http://localhost:4000/admin/sources/auth-status
# 列出最近抛 AdapterAuthError 的源 + 错误原因
# 多半是 cookie 过期或被风控，需要更新 config.cookie

3. 流水线人工放行

合规复核（REVIEW 队列）

# 看待复核列表
curl http://localhost:4000/admin/pipeline/review-queue

# 看某条文章的合规理由（compliance_reasons 字段）
curl 'http://localhost:4000/admin/items?id=<itemId>'

# 放行
curl -X POST http://localhost:4000/admin/pipeline/approve-review/<itemId>

# 拒绝
curl -X POST http://localhost:4000/admin/pipeline/reject-review/<itemId>
放行就是背书。系统标 REVIEW 是因为某个维度评分 ≥ 2，看 compliance_reasons.reasons 里的具体维度和理由再决定。

批量发布

# 看待发布列表
curl http://localhost:4000/admin/pipeline/publish-queue

# 批量放行（itemIds 数组）
curl -X POST http://localhost:4000/admin/pipeline/approve-publish \
  -H 'content-type: application/json' \
  -d '{"itemIds":["id1","id2","id3"]}'

# 单个强制发布（绕过 strict 检查）
curl -X POST http://localhost:4000/admin/day5/force-publish/<itemId>

分发到社媒

# 看单条 / 全部分发任务
curl http://localhost:4000/admin/day6/distribution

# 给单篇生成分发任务（默认 channel=twitter）
curl -X POST http://localhost:4000/admin/day6/distribute/<itemId>

# 批量给所有 PUBLISHED 但还没分发的文章生成分发任务
curl -X POST http://localhost:4000/admin/day6/distribute-all

# 确认分发任务已实际发出（人工或外部 worker 操作完后回调）
curl -X POST http://localhost:4000/admin/pipeline/confirm-distribution/<taskId>

4. 全局控制

急停

# 全部 agent 停调度（已在跑的 job 不打断）
curl -X POST http://localhost:4000/admin/pipeline/emergency-stop

# 恢复
curl -X POST http://localhost:4000/admin/pipeline/resume

暂停 / 启用单个 agent

# 暂停 compliance（不再消费新 job）
curl -X POST http://localhost:4000/admin/pipeline/set-paused \
  -H 'content-type: application/json' \
  -d '{"agent":"compliance","paused":true}'

# 关闭某 agent 的自动模式（不再被 auto-pipeline 自动补单）
curl -X POST http://localhost:4000/admin/pipeline/set-auto \
  -H 'content-type: application/json' \
  -d '{"agent":"ingestion","auto":false}'

看当前各 agent 状态

curl http://localhost:4000/admin/pipeline/state
# 返回每个 agent 的 auto/paused 开关 + 全局 emergency 状态

5. 单条文章的处理

看全链路历史

curl http://localhost:4000/admin/pipeline/item-history/<itemId>
# 列出该 item 在 agent_runs 里的每一次调用：哪个 agent、什么状态、耗时、成本、错误

从某一步重跑

# 重跑 classify-title
curl -X POST 'http://localhost:4000/admin/day3/reclassify/<itemId>'

# 重跑 cover
curl -X POST http://localhost:4000/admin/day4/recover/<itemId>

# 重跑 compliance
curl -X POST http://localhost:4000/admin/day4/recheck/<itemId>

# 通用：从某状态开始重跑（rerun 自动判断从哪步起跑）
curl -X POST http://localhost:4000/admin/pipeline/rerun/<itemId>

回滚到上一状态

curl -X POST http://localhost:4000/admin/pipeline/rollback/<itemId>
# 例如把 PUBLISHED 退回 COMPLIANCE_PASS（文章会从网站消失）

6. 数据查询

整体统计

curl http://localhost:4000/admin/stats
# 返回每个状态的 items 计数、各 agent 最近 24h 成功/失败数

看每天的 GA4 数据

curl http://localhost:4000/admin/day6/analytics

# 立即拉一次（不等每天 2 点的 cron）
curl -X POST http://localhost:4000/admin/day6/analytics-pull

本周报表（markdown）

curl http://localhost:4000/admin/day6/report

直接查库（更灵活）

# 各 agent 最近 24h 成本
SELECT agent, COUNT(*) runs, SUM(cost_usd) cost
FROM agent_runs
WHERE started_at > NOW() - INTERVAL '1 day'
GROUP BY agent
ORDER BY cost DESC NULLS LAST;

# 卡在某状态的 items
SELECT id, status, title, updated_at
FROM items
WHERE status = 'COMPLIANCE_REVIEW'
ORDER BY updated_at DESC LIMIT 50;

# 最近失败的 agent_runs
SELECT agent, item_id, error, started_at
FROM agent_runs
WHERE status = 'failed'
ORDER BY started_at DESC LIMIT 50;

7. 常见运维场景

场景：队列突然堆积

  1. curl /admin/day7/queues 看具体哪个队列堆
  2. 看是不是被人暂停了：curl /admin/pipeline/state
  3. 看 failed 是否在涨：curl /admin/day7/agent-runs?status=failed
  4. 有失败堆积，跑批量重试脚本：scripts/retry-failed.ts（找技术同事跑）
  5. 排查不出来就联系开发

场景：LLM 调用大面积失败

  1. 看 agent_runs.error 字段确认错误码（429 / 5xx 多半是 LLM 服务故障）
  2. 临时降级：在 .env 设全部 *_SKIP_LLM=1 重启 API
  3. 等 LLM 服务恢复后取消降级，跑 retry-failed.ts 重试失败的 job

场景：合规 REVIEW 队列堆得很多

多半是 LLM 调不通，所有不确定的全进了 REVIEW（保守 fallback）。

  1. 确认 LLM 是否恢复：curl -X POST /admin/day1/test-llm
  2. 恢复后批量重检：POST /admin/day4/recheck/<itemId> 一条条重跑（或写循环脚本）

场景：某个信源连续抓不到东西

  1. curl /admin/sources/auth-status 看是否认证失败
  2. 认证失败 → 更新 config.cookie / config.userAgent
  3. 非认证问题 → 找技术同事看 adapter 日志（通常是源站改版）
  4. 临时方案：把灰度调到 0 或 status=inactive，避免反复失败污染指标

场景：发布后网站没刷新

  1. 看 API 日志有没有 [publishing] revalidate failed
  2. 检查环境变量 WEB_URL 和 REVALIDATE_SECRET 是否正确
  3. 手动触发 revalidate： 
    curl -X POST http://<web>/api/revalidate \
  -H "x-revalidate-secret: <your-secret>" \
  -H 'content-type: application/json' \
  -d '{"paths":["/","/a/<slug>"]}'

场景：分发推文文案不合适

  1. "待分发"页面直接编辑文案重新保存
  2. 不想 LLM 重写整个文案，可以改 distribution_tasks.copy 字段后发出

场景：误发了一篇文章想下架

curl -X POST http://localhost:4000/admin/pipeline/rollback/<itemId>
# 状态退回 COMPLIANCE_PASS，published_url 清空，下次 ISR 刷新后从站点消失

CDN 缓存可能让网站继续显示一段时间，必要时联系运维清缓存。

场景：想看上周的 LLM 总开销

SELECT agent, model,
       COUNT(*) calls,
       SUM(cost_usd) cost
FROM agent_runs
WHERE started_at > NOW() - INTERVAL '7 days'
  AND cost_usd > 0
GROUP BY agent, model
ORDER BY cost DESC;

8. 每日 / 每周 checklist

每日（10 分钟）

  1. health 200，队列没异常堆积
  2. 处理 REVIEW 队列里的待复核（≤ 1 小时回应）
  3. 看一眼 alerts，没新告警
  4. 选稿发布 + 分发到社媒

每周（30 分钟）

  1. 看本周报表（/admin/day6/report），整理 Top 10 反馈给内容团队
  2. 看信源得分排行，把分数 < 30 的源考虑暂停
  3. 看 LLM 总开销，对比预算
  4. 清理 failed 队列里的陈年错误（scripts/clear-failed.ts）
  5. 看哪些信源认证失败 → 更新 cookie

9. 紧急联系

需要立即找技术同事的情况
  • health 接口 500，且重启 API 后还是 500
  • 所有队列都没人消费（worker 全挂）
  • 数据库连不上 / Redis 连不上
  • 线上文章页面大面积 500
  • 合规出现明显误判（涉政、涉黄漏过去）
可以等下一个工作日再说
  • 某个信源不工作了（先 inactive 它）
  • LLM 偶发失败（fallback 会兜住）
  • 分发推文偶尔抽风（人工编辑后发出即可）
  • 数据回流缺一两天（GA4 有时候会延迟）

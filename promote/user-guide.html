1. 系统概览

内容中台是一套 9-Agent 自动化内容流水线：从 RSS / HTML 拉取文章 → LLM 分类打标 → 生成标题 → 选配封面 → 合规审查 → 发布上站 → 社媒分发 → T+1 数据分析。

核心能力

  • 自动化 每小时定时 fan-out 所有激活源，items 一路自动流转
  • 人工可控 3 道人工关卡（合规、发布、分发）不会自动放行
  • 可观察 Workbench UI 实时显示每个 Agent 的待处理数、成本、队列状态
  • 可插拔 LLM 当前用 Groq 免费档（llama-3.1-8b-instant），可换 Anthropic / OpenAI / 任意 OpenAI 兼容 endpoint
  • 幂等安全 BullMQ jobId 去重、SHA256 URL 指纹、SimHash 内容去重

系统拓扑

层组件作用
前端Next.js 14 App Router站点 + Workbench 控制台
后端Fastify + BullMQAPI + 9 个 worker 进程
存储PostgreSQL 16sources / raw_items / items / agent_runs / analytics_daily / distribution_tasks
队列Redis 7 + BullMQ9 个命名队列
对象存储MinIO（S3 协议）封面多尺寸图
LLMGroq（免费）分类 / 标题 / 合规打分 / 封面文案

2. 快速启动

前置要求

  • Node.js ≥ 18, pnpm ≥ 8
  • Docker + Docker Compose
  • Groq API Key（免费，去 console.groq.com 申请）

五步启动

# 1. 起基础设施（Postgres + Redis + MinIO）
pnpm infra:up

# 2. 跑数据库迁移
pnpm migrate

# 3. 种入示例采集源（6 个历史类 RSS）
pnpm seed

# 4. 起 API 和 Web 前端
pnpm dev
# 会同时启动:
#   API:  http://localhost:4000
#   Web:  http://localhost:3000

# 5. 打开浏览器访问 workbench
open http://localhost:3000/workbench
成功标志：API 日志出现 workers started: 9 和 Server listening at http://0.0.0.0:4000。

4. 9 个 Agent 的职责

1Source 评分
2内容采集
3分类打标
4标题生成
5封面选图
6合规审查
7发布上站
8社媒分发

#Agent干什么LLM人工
1source-scoring给每个源打质量/稳定性/风险分，决定采集优先级否—
2ingestion拉 RSS / HTML，去重后存 raw_items + items（INGESTED）否—
3classificationLLM 分类为 16 个预设 category + 抽 tags / keywords是—
4titleLLM 生成 3 候选标题、选最优、写 120~180 字摘要是—

6compliance黑名单正则 + LLM 对 6 维度（政敏/色/暴/版/医/金）打分是⚠ 机器建议复核
7publishing写 slug、触发 ISR revalidate否🔐 发布需点批准
8distribution为已发布文章生成 X/Twitter 文案是🔐 复制文案后手动发
9analyticsT+1 从 GA4 拉 PV/UV → analytics_daily否—

5. 数据流与状态机

items 表状态流转

INGESTED          ← ingestion worker 插入时的初始状态
    ↓  classification 完成
CLASSIFIED
    ↓  title 完成
TITLED
    ↓  cover 完成
COVERED
    ↓  compliance 完成
COMPLIANCE_REVIEW ← 机器判定有风险，等人工审核
COMPLIANCE_PASS   ← 人工批准 或 机器直接判过
COMPLIANCE_FAIL   ← 人工拒绝 或 机器判明显违规
    ↓  人工点「批准发布」
PUBLISHED         ← 站点可见
    ↓  distribution 生成文案后
DISTRIBUTED       ← 人工点「已发出」后

Worker 交接链路

每个 worker 完成后直接把下一个 job 塞进队列，不等 auto-pipeline 轮询：

ingestion → classification → title → cover → compliance
                                                  ↓
                                     (人工批准) → publishing
                                                  ↓
                                     (人工确认) → distribution

auto-pipeline（默认 4 秒轮询）作为兜底，定期检查有没有被漏下的 item，把它们补进队列。

6. 三道人工关卡

⚠ 合规复核 · 位置：「流水线」tab 合规审查卡片下方
触发条件：LLM 在 6 个维度（政敏/色低俗/暴恐/版权/医疗夸大/金融诱导）里有任意一项评分 ≥2
你要做什么：
  • 看风险标签（红色 chip）和文章摘要，判断是否真有问题
  • 点 ✓ 批准 → item 转 COMPLIANCE_PASS
  • 点 ✗ 拒绝 → 填拒绝原因 → item 转 COMPLIANCE_FAIL，不会再参与后续流程
🔐 发布关卡 · 位置：发布上站卡片下方
触发条件：item 到达 COMPLIANCE_PASS 状态
你要做什么：
  • 勾选要发布的文章（或全不选即等于批准全部）
  • 点 批准全部 N 篇 / 批准选中 K 篇
  • 后端写 slug、触发 Next.js ISR revalidate，站点立即可见
🔐 分发关卡 · 位置：社媒分发卡片下方
触发条件：item 达到 PUBLISHED 后，点「执行」按钮生成文案
你要做什么：
  • 点「复制文案」把 LLM 生成的推文复制走
  • 手动发到 X / Twitter / 其它平台
  • 发完回来点 ✓ 已发出 记录

7. Workbench 操作手册

地址：http://localhost:3000/workbench

7.1 顶部 Header

  • 冲刺开始 日期选择器：修改后所有 Agent 卡片的 "Day N" 标签会以此为基准换算成真实日期
  • 总计 / 队列 / 成本 三个实时数字
  • 🛑 紧急停止 一键把所有 Agent 的 auto 模式关掉、设 globalStop=true。再点一次「▶ 恢复运行」解除

7.2 三个 Tab

流水线

  • 9 张卡片从上到下对应 9 个 Agent
  • 每张卡片：大数字是待处理数；右边 3 个按钮 ⚡ 自动/手动、⏸ 暂停、▶ 执行
  • ⚡ 自动：auto-pipeline 会自动把满足条件的 item 塞进这个队列
  • ⏸ 暂停：worker 不再处理该队列的新 job
  • ▶ 执行：立刻手动触发一批（当 auto 关闭时用）

采集源

  • + 添加来源 展开表单：名称 / Feed URL / platform / ID 四个字段，点紫色「添加」按钮保存
  • 每个源右侧 4 按钮：活跃/停用（切换 status）、采集（同步拉取一次）、编辑、删除
  • 「删除」如果该源下已有文章，会弹二次确认框问你是否级联删除

队列 & 成本

  • 左表：9 个队列的 等待 / 运行 / 完成 / 失败 数
  • 右表：最近 24h 每个 Agent 的 成功 / 失败 / 平均耗时 / 累计成本

8. 采集源管理

8.1 支持的 platform

platform适用config 必填备注
rssRSS / Atom feedfeed_url, limit默认模式，UI 表单直接支持
html固定 URL 列表urls: string[]不会自动发现文章，得提前列好 URL；UI 表单暂不支持，需 curl 塞

8.2 怎么找一个网站的 RSS URL

  1. 猜路径：网址后面挨个试 /feed, /rss, /atom.xml, /index.xml, /?feed=rss2。WordPress 站基本都有 /feed
  2. 源代码：浏览器查看网页 HTML 源码，搜 application/rss+xml，里面的 href 就是
  3. RSSHub：rsshub.app 提供 800+ 路由，支持微博/知乎/B 站/Twitter/YouTube 等原本没 RSS 的平台
  4. Google News 搜索 RSS：https://news.google.com/rss/search?q=关键词&hl=zh-CN&gl=CN&ceid=CN:zh-Hans
  5. 平台套路：
    • Reddit：https://www.reddit.com/r/话题/.rss
    • YouTube 频道：https://www.youtube.com/feeds/videos.xml?channel_id=UCxxx
    • GitHub 用户：https://github.com/用户名.atom
验证技巧：浏览器直接打开那个 URL，应该看到 <?xml 或 <rss 开头的 XML。看到网页、搜索结果页、302 跳转都不是 RSS。

10. 常见故障排查

10.1 端口 4000 已占用（EADDRINUSE）

tsx watch 偶尔在热重载时旧进程没退出。解决：

lsof -ti :4000 | grep -v 5121 | xargs kill -9
pnpm --filter @ch/api dev &

5121 是 Chrome Helper 的 PID，它把 4000 加到自己的网络池里但并不监听。

10.2 删除源报 FK 违反约束（23503）

错误信息：violates foreign key constraint items_source_id_fkey。

原因：该源下还有 items。方案：

  • 推荐：点「活跃/停用」改为 inactive，源不会再被采集，文章保留
  • 彻底删：点「删除」→ 第一次 confirm → 后端返 409+itemCount → 第二次 confirm → 加 ?cascade=1 级联删除 items

10.3 classification 报 "400 Failed to call a function"

Groq 小模型对 function calling 支持差。我们已切换到 JSON mode：把 tool schema 注入 system prompt，让模型直出 JSON 再反序列化。如果仍失败，检查 anthropic.ts 里的 useJsonMode 分支。

10.4 LLM 报 429 Rate Limit

Groq 免费档 llama-3.1-8b-instant 只有 6000 TPM。

  • LLM worker 并发必须 =1，不能提高
  • 每次调用输入不能太长（已经把 MAX_CONTENT 压到 1200~1800 字）
  • 想彻底摆脱限流：升级 Groq 付费档，或换 Anthropic / OpenAI

10.5 队列大量 "item not found" 失败

通常是刚刚 TRUNCATE 或 级联删除时，worker 正在处理那些 items。是副作用，不影响新数据。清掉：

cd apps/api && ../../node_modules/.bin/tsx scripts/clear-failed.ts

10.6 "Feed not recognized as RSS 1 or 2"

填的 URL 不是合法 RSS（比如百度 / 谷歌搜索跳转链接、普通网页）。用 8.2 的方法找到真正的 feed URL，编辑源修正。

10.7 publishing 日志报 revalidate failed 404

Next.js 那边没有 /revalidate 路由。不影响发布：item 已经标 PUBLISHED，只是没触发 ISR 主动刷新。打开页面刷新一次即可。要彻底解决就在 apps/web 加个 /revalidate API Route。

端到端参考

  • 6 个 RSS 源，每源 15 条 = 90 条：从点 fanout 到全部发布完，约 2-3 分钟

  • Groq 成本：免费档 0 元；换 Anthropic Haiku 约 $0.0002/条，换 Opus 约 $0.003/条

12. 常用命令速查

系统

pnpm infra:up             # 起 Postgres / Redis / MinIO
pnpm infra:down           # 停
pnpm infra:logs           # 看容器日志

pnpm build                # 全仓库构建

数据库（直连）

# 连上 psql
docker exec -it ch-postgres-1 psql -U ch ch

# 看 items 状态分布
docker exec ch-postgres-1 psql -U ch ch -c \
  "SELECT status, COUNT(*) FROM items GROUP BY status;"

# 看源列表
docker exec ch-postgres-1 psql -U ch ch -c \
  "SELECT external_id, name, status, last_fetch_at FROM sources;"

# 清空所有数据（保留 sources）
docker exec ch-postgres-1 psql -U ch ch -c \
  "TRUNCATE items, raw_items, agent_runs, distribution_tasks, analytics_daily RESTART IDENTITY CASCADE;"

BullMQ 队列

# 看所有队列状态
curl http://localhost:4000/admin/day7/queues | jq

# 清空所有失败任务
cd apps/api && ../../node_modules/.bin/tsx scripts/clear-failed.ts

# 摧毁所有队列（含等待、运行、失败、完成）
cd apps/api && ../../node_modules/.bin/tsx scripts/cleanup-queues.ts

# 重试所有失败任务
cd apps/api && ../../node_modules/.bin/tsx scripts/retry-failed.ts

API 调试

# 触发一次全局 fanout
curl -X POST http://localhost:4000/admin/ingest/fanout

# 触发单个源同步采集
curl -X POST http://localhost:4000/admin/ingest/<SOURCE_ID>

# 看 pipeline 全局状态

# 紧急停止
curl -X POST http://localhost:4000/admin/pipeline/emergency-stop
